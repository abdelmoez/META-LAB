# PecanRev — Manuscript Live Synchronization, Search Provenance, Change Tracking, and Newcastle–Ottawa Scale

I want you to implement the following changes in PecanRev as a cohesive system, not as isolated patches.

You may use as many agents, subagents, code reviews, test passes, and implementation iterations as necessary. Take the time needed to understand the existing architecture before changing anything. Inspect how the Search Engine, Screening Engine, Extraction Engine, Analysis Engine, Risk of Bias system, project history/audit log, and Manuscript Editor currently communicate with each other.

The central principle is:

> **The Manuscript Editor must be a live, evidence-backed representation of what actually happened in the research project.**

It should never become a collection of stale templates that the researcher must manually refresh.

Every statement generated automatically in the manuscript should be traceable to the project data and should update intelligently when the underlying methodology or results change.

---

# 1. Search Engine → Manuscript Editor synchronization

The manuscript's search-methodology paragraph must be generated dynamically from the actual search history.

This applies equally to:

* Manual Search
* Automated Search
* Hybrid workflows where the researcher uses automated search for some databases and manual search for others
* Repeated searches
* Updated searches
* Living-review searches, if applicable
* Any future search method added to PecanRev

Do not hard-code assumptions about one particular search workflow.

## Databases searched

The manuscript should automatically identify and state which databases were actually searched.

For example, if the project searched:

* PubMed/MEDLINE
* Embase
* Scopus
* Web of Science

the Methods section should reflect those databases automatically.

Do not rely on a manually entered list.

The manuscript should derive this from the project's actual search execution/history.

If the researcher later adds another database, such as CENTRAL, the manuscript should update automatically where appropriate.

If a database was configured but never actually searched, it should not be represented as though it had been searched.

Maintain enough provenance to distinguish things such as:

* configured database
* attempted search
* successfully completed search
* search producing zero results
* failed search
* manually imported search results
* subsequently removed/invalidated search

Use good methodological judgment when determining what belongs in the final manuscript.

---

# 2. Automatically record and use the latest search date

The manuscript should automatically include the date of the most recent valid search.

For example:

> "The databases were searched from inception through August 6, 2026."

Do not make the user manually enter or update this date.

The system must determine it from the project's actual search history.

If the researcher runs an updated search on a later date, the manuscript should automatically update.

However, this must be **intelligent rather than naïve**.

A trivial action that does not alter the meaningful search record should not unnecessarily rewrite the manuscript.

Examples:

### Should normally update the manuscript

* Running an additional database search
* Re-running the literature search at a later date
* Changing the final search strategy and executing it
* Adding a database
* Removing an invalid database search
* Correcting a search that subsequently changes the records entering screening
* Performing an updated search for a living systematic review

### Should not necessarily rewrite the methodology

* Merely opening the Search Engine
* Viewing a search string without executing it
* Editing something and reverting it before execution
* Running a failed test search that never becomes part of the research workflow
* UI-only changes

Design a proper event/provenance model rather than listening blindly to every frontend state change.

---

# 3. Search changes must propagate throughout the research project

This is particularly important.

Search updates should not stop at rewriting one paragraph.

If a meaningful search modification changes the actual body of evidence, PecanRev must propagate the consequences through the research workflow.

Think in terms of a dependency graph.

For example:

Search changes
↓
Retrieved records change
↓
Deduplication may change
↓
Screening population changes
↓
PRISMA counts may change
↓
Included studies may change
↓
Extraction may change
↓
Risk of Bias population may change
↓
Analysis may change
↓
Figures/tables/results may change
↓
Manuscript Methods/Results/Abstract/Discussion may need updating

Do not silently leave downstream sections inconsistent.

The system should determine which downstream components are affected and mark/recompute/update them appropriately.

This must work for both:

* Manual Search
* Automated Search

and mixtures of the two.

---

# 4. The Manuscript Editor should be continuously synchronized

I do **not** want users to press:

* Refresh manuscript
* Regenerate
* Update text
* Sync
* Apply project changes

or anything equivalent.

The manuscript should stay synchronized automatically.

Whenever a meaningful project change occurs, the corresponding manuscript content should update automatically.

This includes changes originating from:

* Protocol
* Search
* Screening
* Deduplication
* Full-text review
* Study inclusion/exclusion
* Extraction
* Risk of Bias
* Statistical Analysis
* Meta-analysis settings
* Sensitivity analyses
* Subgroup analyses
* Network meta-analysis
* Figures
* Tables
* PRISMA flow
* Study characteristics
* Any other engine capable of changing information described in the manuscript

The synchronization system should be reliable enough that a researcher can trust that the manuscript represents the current state of the project.

---

# 5. Do not overwrite genuinely human-authored prose unnecessarily

Automatic synchronization must not make the manuscript frustrating to write.

You need to distinguish between:

1. **System-managed factual/methodological content**
2. **Human-written interpretation and narrative**
3. **Mixed sections containing both**

For system-derived facts, PecanRev should update the underlying facts automatically.

For human prose, preserve the user's writing whenever possible.

For example, if a researcher writes:

> "These findings suggest that the intervention may be especially useful in high-risk populations."

a search update should not destroy this sentence merely because the Results numbers changed.

Instead, update the factual components that depend on project data and flag human-written interpretations that may have become inconsistent.

Build this intelligently.

Do not solve synchronization by regenerating the entire manuscript after every change.

# 6. Manuscript Change Tracking toggle

Add a clean toggle in the Manuscript Editor for something similar to:

**Show Changes**

You may choose better wording if UX testing shows something clearer.

When OFF:

The manuscript should look like a normal clean manuscript.

No distracting provenance markers should remain visible.

When ON:

Show a visual overlay indicating automatically updated manuscript content.

The underlying manuscript content should be identical in both modes.

The toggle only changes the visualization of provenance/change history.

For example:

* Search Engine
* Screening Engine
* Extraction Engine
* Risk of Bias
* Analysis Engine
* Protocol
* Manual manuscript edit
* PRISMA
* Other relevant project modules

Use a restrained, accessible color system.

Do not turn the manuscript into a rainbow.

Colors should be:

* visually distinct
* accessible
* readable in light/dark themes if supported
* subtle enough for professional use
* accompanied by icons/labels/tooltips where necessary so color is never the only indicator

# 8. Show what changed

When change tracking is enabled, users should be able to understand the actual modification.

For example:

Previous:

> "Three databases were searched through July 1, 2026."

Updated:

> "Four databases were searched through August 6, 2026."

The system should be capable of showing that:

* "Three" became "Four"
* "July 1, 2026" became "August 6, 2026"
* The change originated from the Search Engine
* The change occurred at the corresponding date/time
* Ideally what project action triggered it

Do not make this intrusive during normal writing.

---

# 9. Hover/click provenance details

When Show Changes is enabled, hovering over or clicking a changed segment should expose useful metadata.

Example:

**Updated by:** Search Engine
**Changed:** August 6, 2026
**Reason:** Updated PubMed and Embase searches executed
**Previous value:** July 1, 2026
**Current value:** August 6, 2026
**Affected manuscript field:** Methods → Information Sources/Search Strategy

Potential additional metadata:

* user responsible for triggering the underlying project change
* source engine
* event ID
* database involved
* old value
* new value
* related version
* dependent sections affected

Do not expose internal technical information that has no value to researchers.

---

# 10. Revert individual automatic manuscript changes

Users should be able to inspect an automatic manuscript modification and revert it if they believe the prior wording was more accurate.

For example:

Current automatically updated text:

> "The databases were searched through August 6, 2026."

If the researcher determines that the August search was only exploratory and should not be reported, they should be able to restore the earlier representation.

However, this must not silently falsify the underlying research history.

The system needs to distinguish between:

* reverting manuscript wording
* reverting the underlying project event

These are not necessarily the same thing.

If reverting manuscript wording creates a discrepancy with project data, clearly communicate this.

Potentially allow options such as:

* Restore previous wording
* Revert underlying project change, where technically and scientifically valid
* Keep current wording

Use appropriate safeguards.

---

# 11. Ctrl+Z / Cmd+Z undo

Support intuitive undo behavior in the Manuscript Editor.

At minimum:

* `Ctrl + Z` on Windows/Linux
* `Cmd + Z` on macOS

should undo manuscript changes appropriately.

It should work with:

* manual text edits
* accepted/reverted automatic updates where appropriate
* formatting operations
* suitable manuscript version actions

Do not make Ctrl+Z unexpectedly undo a major research analysis or delete screening data simply because the manuscript changed as a consequence.

Separate manuscript editing history from underlying research workflow history.

If users want to revert a research workflow operation, that should occur through the appropriate project/history mechanism.

---

# 12. Every revert must be audited

Whenever an automatically updated manuscript element is reverted, record it in the project's audit history.

Record information such as:

* timestamp
* user
* manuscript section
* previous version
* reverted version
* source engine
* related project event
* whether the revert affected manuscript text only or underlying research data
* subsequent override if applicable

This history must be append-only enough that important research provenance cannot simply disappear.

A researcher should eventually be able to answer:

> "Why does the manuscript currently say this?"

and PecanRev should provide a defensible history.

* manual revisions
* grouped transactions
* timestamps
* responsible user
* before/after content

Use a sensible strategy such as:

* operation logs
* diffs
* snapshots/checkpoints
* version tables
* transaction grouping

Choose the architecture that is most reliable and scalable.

# 14. Group related automatic changes

If one underlying action changes multiple manuscript values, group them intelligently.

For example, running an updated search might change:

* final search date
* number of databases searched
* total records identified
* duplicate count
* title/abstract screening count
* PRISMA diagram
* final included study count

The user should not receive 15 unrelated change notifications.

Represent this as a coherent research event such as:

**Updated literature search — August 6, 2026**

Then allow the researcher to inspect the consequences.

---

# 15. Intelligent dependency and invalidation system

Do not simply regenerate everything whenever anything changes.

Introduce or improve dependency tracking.

Examples:

### Search terms changed but search not executed

Probably no downstream invalidation.

### Search executed and no new records found

Search date may update.

PRISMA/search methodology may update.

Extraction and analysis may not require recomputation.

### Search executed and 35 new records added

Screening becomes affected.

PRISMA changes.

Analysis should not immediately assume those records are included.

### New study passes screening

Extraction/Risk of Bias may become incomplete.

Analysis may need to be marked as requiring update.

### Extracted outcome value changes

Relevant analyses must be recalculated.

Results text/tables/figures may change.

### Meta-analysis model changes from fixed-effect to random-effects

Analysis changes.

Methods, Results, tables, figures, and possibly Abstract should update.

This dependency model is extremely important.

---

# 16. Manuscript synchronization must be transactional

Avoid partial states.

For example, do not allow a situation where:

* the Results paragraph says 12 studies,
* the PRISMA diagram says 13,
* the forest plot contains 11,
* and the Abstract says 10.

When an operation affects multiple manuscript components, update them as one coherent transaction where possible.

If some downstream calculation is still pending, show that the affected manuscript content is temporarily stale/pending instead of presenting contradictory information as current.

---

# 17. Scientific accuracy is more important than immediate text generation

The manuscript automation must never fabricate methodology.

If the underlying project does not contain enough information, do not invent it.

Examples:

Do not claim:

> "Two independent reviewers screened all records"

unless the project history confirms that workflow.

Do not claim:

> "Disagreements were resolved by consensus"

unless that actually occurred or is an explicitly defined protocol process.

Do not claim:

> "Embase was searched"

because Embase was selected in a settings page.

It must actually have been searched according to project records.

This principle should apply across the Manuscript Editor.

---

# 18. Add Newcastle–Ottawa Scale to Risk of Bias

Add proper support for the **Newcastle–Ottawa Scale (NOS)** within PecanRev's Risk of Bias / Quality Assessment functionality.

Do not simply add "Newcastle Ottawa" as another dropdown option.

Implement it properly.

NOS is primarily used for non-randomized observational studies, particularly:

* cohort studies
* case-control studies

Design the workflow appropriately for study type.

---

# 19. Newcastle–Ottawa Scale — cohort studies

Support the standard cohort NOS structure.

The tool generally evaluates three major domains:

### Selection

* Representativeness of the exposed cohort
* Selection of the non-exposed cohort
* Ascertainment of exposure
* Demonstration that outcome of interest was not present at start of study

### Comparability

* Comparability of cohorts on the basis of design or analysis

### Outcome

* Assessment of outcome
* Was follow-up long enough for outcomes to occur?
* Adequacy of follow-up of cohorts

Implement the appropriate star-based scoring structure.

Do not merely create a generic 0–9 input.

The user should actually perform the assessment using the NOS criteria.

---

# 20. Newcastle–Ottawa Scale — case-control studies

Support the case-control variant separately.

Typical domains include:

### Selection

* Adequacy of case definition
* Representativeness of cases
* Selection of controls
* Definition of controls

### Comparability

* Comparability of cases and controls based on design or analysis

### Exposure

* Ascertainment of exposure
* Same method of ascertainment for cases and controls
* Non-response rate

Again, implement the actual domain structure rather than one numeric field.

---

# 21. NOS scoring

Properly calculate stars according to NOS logic.

Normally the maximum is 9 stars:

* Selection: up to 4
* Comparability: up to 2
* Outcome/Exposure: up to 3

Verify this against authoritative Newcastle–Ottawa documentation before implementation.

Do not rely solely on memory or assumptions.

---

# 22. Avoid inventing universal NOS quality thresholds

Be careful with arbitrary labels such as:

* 0–3 poor
* 4–6 moderate
* 7–9 high quality

There is no universally accepted single categorization across all research contexts.

If PecanRev supports interpretation thresholds, they should either:

* be user-configurable,
* follow a specifically documented protocol,
* or be represented clearly as project-defined thresholds.

Do not imply that one arbitrary threshold is an official NOS rule.

This matters scientifically.

The user should be able to:

* select an assessment option

* add rationale/comments

# 27. Manuscript integration for NOS

The Manuscript Editor should know which Risk of Bias/quality assessment tool was actually used.

If the project uses NOS, the Methods section should automatically describe it accurately.

For example, the manuscript might appropriately state that observational study quality was assessed using the Newcastle–Ottawa Scale and specify the relevant study designs.

Do not insert the statement merely because NOS exists as an available option.

Only include it if it was actually used.

If the project uses multiple assessment tools for different study designs, the manuscript should describe that intelligently.

For example:

* RoB 2 for randomized trials
* ROBINS-I for non-randomized intervention studies
* Newcastle–Ottawa Scale for eligible cohort/case-control studies

The wording should reflect actual project usage.

# 30. Materiality logic

Not every change deserves manuscript modification.

Create an explicit concept of **material project change**.

Examples of material changes:

* search executed
* study inclusion status changed
* primary outcome changed
* extracted value changed
* analysis method changed
* effect measure changed
* statistical model changed
* risk assessment finalized
* new study added

Examples likely not material:

* panel resized
* tab changed
* search field focused
* concept accordion expanded
* manuscript scrolled
* UI preference changed

Separate domain events from UI events.

# Definition of Done

I will consider this implementation successful when I can perform this workflow:

1. Create a systematic review.
2. Run automated searches in PubMed and Embase.
3. Manually search another database.
4. Open the manuscript.
5. See the correct databases and most recent valid search date automatically.
6. Screen the studies.
7. See screening/PRISMA information update automatically.
8. Extract studies.
9. Perform Newcastle–Ottawa assessments for observational studies.
10. Run the analysis.
11. See the relevant Methods/Results text update automatically.
12. Change the analysis method.
13. See the manuscript update without pressing any refresh button.
14. Turn on **Show Changes**.
15. See which wording changed, which PecanRev engine caused it, and when.
16. Hover/click a change and understand why it changed.
17. Revert an appropriate manuscript change.
18. See that revert reflected immediately and recorded in the audit history.
19. Use Ctrl+Z/Cmd+Z appropriately.
20. Turn Show Changes off.
21. See a completely clean manuscript.
22. Export the manuscript without provenance overlays.
23. Have confidence that the manuscript accurately represents the current research project.

Before declaring completion, run the full test suite, add tests for the new behavior, inspect the final UX directly, test realistic projects with manual search, automated search, mixed search, observational studies, multiple reviewers, and downstream analysis changes, and resolve inconsistencies you discover.

The most important principle throughout this implementation is:

> **PecanRev must maintain one synchronized source of scientific truth. Search, screening, extraction, risk of bias, analysis, PRISMA, tables, figures, and manuscript text should never behave like disconnected applications.**
