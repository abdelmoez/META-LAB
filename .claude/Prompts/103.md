I want you to perform a **complete redesign and audit of the PRISMA Flow system in PecanRev**.

This is not just a visual change to the PRISMA diagram. I want the PRISMA flow to become a **live, continuously synchronized representation of everything that has happened in the project that affects study/article counts**.

The PRISMA information must always reflect the real state and history of the systematic review.

## Core principle

The PRISMA flow should **never depend on the user manually entering numbers that PecanRev already knows**.

If an action anywhere in the project changes, adds, removes, excludes, retrieves, deduplicates, imports, or otherwise affects the number of records or studies at any PRISMA stage, the PRISMA system should know about it and update automatically.

I want you to first perform a full review of the current application architecture, workflows, databases, Search Engine, Screening Engine, deduplication system, manual imports, automated search, manual search, full-text workflow, exclusions, and manuscript integration.

Then compare the current behavior against the **PRISMA 2020 flow diagram and reporting principles** and determine what the system should actually be tracking.

Do not immediately start patching individual counters. First understand the complete lifecycle of a record inside PecanRev.

---

Before implementing anything, identify every way a record can enter, move through, or leave the project.

This should include, but should not be limited to:

* Automated database searches
* Manual database searches
* Search results imported from external databases
* Uploaded RIS files
* Uploaded BibTeX files
* CSV imports
* PMID/DOI/manual citation imports
* Manually added articles
* Citation mining
* Backward citation searching
* Forward citation searching
* Living review searches
* Search reruns
* Search updates
* Duplicate detection during automated searching
* Duplicate detection during import
* Duplicate detection inside the Screening Engine
* User-confirmed duplicate removal
* Automatically confirmed duplicates
* Records removed for other reasons
* Title/abstract screening
* Full-text retrieval
* Full-text screening
* Full-text exclusion
* Conflicts
* Second reviewer decisions
* Studies included in qualitative synthesis
* Studies included in quantitative synthesis/meta-analysis
* Reports with multiple publications representing the same study
* Articles removed manually by authorized users
* Records restored after deletion/exclusion where supported
* Any future source of studies already represented in the architecture

Search the codebase comprehensively and find every pathway that can affect these counts.

Do not assume the list above is exhaustive.

---

# 2. Automated searches must update PRISMA correctly

If PecanRev performs an automated search, every database/source should contribute accurately to the PRISMA record.

For example, if an automated search finds:

* PubMed: 1,200 records
* Embase: 1,500 records
* Scopus: 800 records

and the automated search process itself detects 600 duplicates before sending records into screening, PRISMA must understand and display that correctly.

The duplicate count must not disappear simply because deduplication happened before the Screening Engine.

The system needs to distinguish between:

* records identified,
* duplicate records removed,
* records remaining after deduplication,
* and records entering screening.

If there are multiple database searches, preserve enough source information to reconstruct where records came from.

---

# 3. Screening Engine deduplication must also update PRISMA

If the user later enters the Screening Engine and runs **Detect Duplicates**, any newly identified duplicate records should update PRISMA automatically.

This means PRISMA needs to understand that duplicates may be removed at different stages.

For example:

* 500 duplicates removed automatically during Search
* another 75 duplicates discovered in Screening

The final PRISMA duplicate count should correctly reflect the total appropriate count without double-counting records.

The underlying system should know which specific records were removed and why.

Do not simply add numbers together blindly.

Use record IDs and event/state tracking so that the same duplicate cannot accidentally be counted twice.

---

# 4. Manual search must be represented

If a user performs a manual literature search through PecanRev, those results must be represented in PRISMA.

If a user manually searches a database and imports 200 results, those 200 records must appear in the appropriate identification source.

The system should record:

* database/source,
* search date,
* number retrieved,
* import batch,
* query/search strategy where available,
* duplicates resulting from the import,
* and how many ultimately entered screening.

Manual searching should not create a disconnected workflow that PRISMA cannot see.

---

# 5. Manually added studies must be represented

If the user adds a study manually, this must update the PRISMA flow appropriately.

Examples include:

* adding a PMID,
* entering a DOI,
* manually creating a citation,
* uploading a single article,
* adding a study discovered outside database searches,
* adding an article from a reference list,
* adding an article discovered from another source.

PRISMA should classify these appropriately instead of pretending that every study came from a database search.

The system should distinguish sources such as:

* databases/registers
* citation searching
* websites
* organizations
* other methods

where relevant under PRISMA 2020.

---

# 6. Citation mining must update PRISMA

If PecanRev supports forward or backward citation searching, the resulting records should be tracked separately from traditional database searching when appropriate.

The PRISMA flow should be able to represent records identified through:

* citation searching,
* reference lists,
* related-article tools,
* forward citations,
* backward citations,
* other non-database methods.

Again, do not just modify a displayed number.

Store the provenance of each imported record.

---

# 7. Search reruns and Living Reviews

This is especially important.

If the user reruns a search later, PRISMA should not simply overwrite the previous search counts.

The system needs to understand search history.

For example:

Initial search:

* 3,000 records retrieved
* 700 duplicates
* 2,300 screened

Updated search six months later:

* 400 new records retrieved
* 350 already existed
* 50 genuinely new records entered screening

The PRISMA system needs to represent this accurately.

Do not count the same existing 350 records as newly screened again.

Design a robust mechanism for:

* initial searches,
* updated searches,
* Living Review updates,
* database reruns,
* new records versus already-known records.

Preserve historical search batches and provenance.

---

# 8. Track exclusions accurately

PRISMA must remain synchronized with screening.

The system should automatically know:

### Records screened

How many unique records entered title/abstract screening.

### Records excluded

How many were excluded during title/abstract screening.

### Reports sought for retrieval

How many proceeded to full-text retrieval.

### Reports not retrieved

How many full texts could not be obtained.

### Reports assessed for eligibility

How many full texts were actually evaluated.

### Reports excluded

How many full-text articles were excluded.

Where exclusion reasons are available, PRISMA should aggregate them correctly.

For example:

* Wrong population: 42
* Wrong intervention: 31
* Wrong outcome: 20
* Wrong study design: 18
* Duplicate publication: 4
* Unable to obtain full text: handled in the appropriate PRISMA category

The totals must reconcile mathematically.

---

# 9. Studies versus reports

This is very important for PRISMA accuracy.

PRISMA distinguishes between **records, reports, and studies**.

Do not assume:

`1 article = 1 study`

There may be:

* multiple publications for one trial,
* conference abstract + full manuscript,
* interim analysis + final analysis,
* subgroup publications,
* secondary analyses of the same cohort.

Review whether PecanRev currently has a concept of linking multiple reports to the same underlying study.

If it does, integrate that into PRISMA.

If it does not, design the architecture so that this distinction can be supported safely without breaking the current workflow.

The final included count should be able to distinguish:

* studies included,
* reports of included studies.

---

# 10. Create a single source of truth

Do not create separate manually synchronized counters all over the application.

I want one reliable underlying PRISMA data model.

Prefer deriving PRISMA counts from:

* article identity,
* source/provenance,
* state,
* screening decisions,
* exclusion reasons,
* search batches,
* deduplication events,
* retrieval state,
* study/report relationships,

rather than storing fragile counters that can drift from the real project.

The UI should be a representation of this underlying truth.

---

# 11. Event/history architecture

I want this integrated with PecanRev's broader project history/logging system.

Every meaningful PRISMA-affecting event should have enough information to reconstruct what happened.

Examples:

* `SEARCH_EXECUTED`
* `RECORD_IMPORTED`
* `RECORD_MANUALLY_ADDED`
* `DUPLICATE_DETECTED`
* `DUPLICATE_CONFIRMED`
* `RECORD_REMOVED`
* `TITLE_ABSTRACT_EXCLUDED`
* `FULL_TEXT_REQUESTED`
* `FULL_TEXT_NOT_RETRIEVED`
* `FULL_TEXT_EXCLUDED`
* `STUDY_INCLUDED`
* `REPORT_LINKED_TO_STUDY`

These names are examples only. Use whatever architecture best fits the existing codebase.

The important requirement is auditability.

For every PRISMA number, we should ultimately be able to answer:

**"Which records created this number?"**

---

# 12. Make PRISMA numbers inspectable

The user should be able to click or otherwise inspect PRISMA counts.

For example, if PRISMA says:

`Duplicate records removed: 742`

the user should be able to inspect where those 742 came from.

Potential breakdown:

* Automated Search deduplication: 510
* Screening Engine deduplication: 180
* Manual duplicate confirmation: 52

Similarly, clicking:

`Reports excluded: 116`

could show the exclusion reason breakdown.

This would make the PRISMA flow transparent and auditable instead of being a mysterious set of numbers.

Keep the normal PRISMA chart visually clean; detailed information can appear on interaction.

---

# 13. Validation and reconciliation engine

Build automated validation checks.

PRISMA numbers should reconcile.

Examples of checks:

`Records identified - records removed before screening = records screened`

and:

`Reports sought for retrieval - reports not retrieved = reports assessed for eligibility`

and:

`Reports assessed - reports excluded = reports included`

Use the correct PRISMA model rather than blindly applying these examples if the real relationships differ.

If there is a mismatch, the application should detect it.

Never silently display mathematically inconsistent PRISMA numbers.

Provide a clear internal warning or admin/debug state identifying where the discrepancy comes from.

---

# 14. Handle deletion and restoration safely

If a user deletes or removes an article after it has already influenced PRISMA, determine what the correct behavior should be.

The counts must remain historically and methodologically accurate.

Do not simply subtract numbers without understanding the event.

For example:

* Was it deleted because it was a duplicate?
* Was it imported accidentally?
* Was it excluded?
* Was a screening decision reversed?
* Was the article later restored?

The model needs to preserve sufficient history to recalculate the flow correctly.

---

# 15. Manuscript Editor integration

The manuscript Methods/Results sections should use the same PRISMA source of truth.

If the manuscript says:

> “The search identified X records, of which Y duplicates were removed...”

those numbers should come directly from the same PRISMA data model.

If the project changes, the manuscript text should update where appropriate.

Do not allow the PRISMA chart and manuscript to disagree.

Similarly, the PRISMA diagram, project statistics, screening counts, and manuscript reporting must all derive from the same underlying information.

# 18. Migration of existing projects

Existing projects may already contain:

* search results,
* duplicates,
* screening decisions,
* full-text decisions,
* included studies,
* manual imports.

Design a safe migration/backfill strategy.

Where possible, reconstruct PRISMA state from existing project data.

Do not destroy existing user data.

If some historical information cannot be reconstructed with certainty, clearly mark that internally rather than inventing information.

---

# 19. Performance

PRISMA should update quickly but should not trigger expensive full-project recalculations unnecessarily after every tiny UI action.

Design an efficient architecture.

Potential approaches may include:

* normalized event/state tables,
* incremental recalculation,
* cached derived counts with invalidation,
* background-safe processing where appropriate,
* database queries optimized around indexed record states.

Choose the architecture that best fits the existing application.

Accuracy is more important than premature optimization, but the system must remain scalable to projects containing tens or hundreds of thousands of records.

# 20. Testing

Create comprehensive automated tests.

At minimum test scenarios such as:

### Scenario A — automated search

5,000 records found → 1,000 duplicates → 4,000 screening records.

### Scenario B — additional duplicate detection

4,000 screening records → another 200 duplicates identified correctly without double-counting.

### Scenario C — manual import

100 records imported manually → 25 already exist → only 75 genuinely new records.

### Scenario D — manually added study

One manually added citation appears in the appropriate PRISMA identification pathway.

### Scenario E — citation searching

Articles added from backward/forward citation searching appear under the correct identification source.

### Scenario F — screening

Records progress accurately through title/abstract → full text → exclusions → inclusion.

### Scenario G — multiple reports per study

Three articles representing one trial produce the appropriate report count while remaining one included study.

### Scenario H — decision reversal

A full-text exclusion changed to include updates the entire flow correctly.

### Scenario I — living review update

Existing records retrieved again are not counted as new unique records.

### Scenario J — deletion/restoration

Counts remain internally consistent and historically correct.

Test both backend calculations and frontend presentation.

**simple on the surface, extremely rigorous underneath.**

## Final requirement

The PRISMA diagram should no longer be thought of as a chart that gets updated.

It should be the **visual output of PecanRev's complete study-selection provenance system**.

Anything that happens anywhere in the project that legitimately affects PRISMA must automatically and accurately propagate into:

* the underlying PRISMA data,
* the visible PRISMA flow,
* project statistics,
* and the Manuscript Editor.

There should be one source of truth, full traceability, no double-counting, no stale numbers, and no need for users to manually keep PRISMA synchronized with the actual review.
