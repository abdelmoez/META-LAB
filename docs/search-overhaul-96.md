# Pecan Search Engine overhaul (96.md) — implementation report

Date: 2026-07-31 · Version: v4.3.0 · Scope: Search Engine simplification + Search→Screening integration

## 1. What changed

The Pecan Search Engine no longer builds searches through PICO. The workflow is now:

**Research Question → Terms & Vocabulary → Search Mode → (Database Strategies) → Results → Documentation → Send to Screening**

- The **Research Question stage** is a prominent editor for the free-text question
  (`project.pico.question` remains the authoritative storage so Protocol, manuscript,
  screening AI, and exports keep working). It claims the same `pico.question`
  collaborative field lock as the Protocol editor.
- The **Concepts page and Search Quality Check page are gone.** Stale deep links
  (`?stage=concepts`, `?stage=refine`) redirect to Terms & Vocabulary with the URL
  rewritten. The legacy 3-step SearchWizard and the `searchWorkspaceV2` flag branch
  were retired; the staged workspace is the only Search surface when the
  `searchEngine` flag is on.
- **Terms & Vocabulary is the single search-building workspace**: question display with
  drift detection, token/span phrase selection that creates concept groups, group
  management (rename, reorder, merge, split, delete — all undoable), synonym and MeSH
  management with structured vocabulary badges, visible between-group AND/OR controls,
  inline quality checks, per-database query previews with live counts, manual
  per-database overrides, and the search-versions panel.
- **Every automated search is a durable run record** (`PecanSearchRun`, extended) with
  origin (user/living-review), question snapshot, strategy-version reference, exact
  per-database executed queries, per-source counts including the new **updated**
  (metadata-merge) counter, and rolled-back status.
- **Screening shows a Search Import History timeline**: each run is a separate event
  ("312 retrieved · 224 new · 76 already present · 3 updated · 12 duplicates skipped ·
  0 failed") with expandable per-database details, error details, pagination, and
  rolled-back badges; file/API imports appear as their own entries.
- **Article-level provenance** (`ScreenRecordSource`) records every search/import that
  found each article across runs and databases; a record drawer section shows "first
  found by…", other sources, and field-level metadata changes (`ScreenRecordMetadataChange`).
- **Safe metadata merge**: re-found records get fill-blank-only enrichment
  (abstract/DOI/PMID/authors/year/journal/keywords) — never overwriting non-empty
  fields, never touching screening decisions/notes/conflicts/attachments; every filled
  field is logged. "Updated" counts as *already present* for PRISMA (rerun-stable).
- **Delete All Imported Search Records**: an owner/admin-only, typed-confirmation,
  transactional reset with two explicit scopes (search-imported only / everything),
  job fencing (in-process reset lock + fail-closed fence re-checked inside the
  transaction + enqueue-side guards + landing-funnel guard), duplicate-group repair for
  surviving records, full bare-scope cleanup, PDF disk cleanup, run rollback marking,
  PRISMA exclusion of rolled-back runs, audit + provenance-ledger events, and
  realtime invalidation. Search strategy and search history remain.

## 2. Architecture

**Search strategy** stays one authoritative structured document per project
(WorkflowModuleState `search`): `concepts[{id,label,sourcePhrase?,op,terms[...]}]` with
per-term structured vocabulary (`vocab{mesh,meshUI,tree,emtree,synonyms,scope,children}`),
`overrides{dbId}`, `filters`, `questionSnapshot`, `dismissedWarnings`,
`rejectedSuggestions`, `databases`, `searchMode`. Legacy PICO-shaped concepts
(`picoField`, `source:'pico_auto'`) load forever; version snapshots/diffs keep their
historical identity. New persisted keys follow the putSearch whitelist + omit-when-empty
byte-stability contract. The PICO→concepts auto-sync was removed; new projects seed
empty and build from question phrase selection.

**Controlled vocabulary** remains structured to render time; each database renderer
flattens at the last moment. Embase Emtree headings are heuristic (derived from MeSH)
and are now flagged `approximate` with an explicit verification warning. 16 preview
compilers exist; 7 databases have real automated-run connectors (PubMed, Europe PMC,
ClinicalTrials.gov, Crossref, DOAJ, OpenAlex, Semantic Scholar).

**Boolean model**: terms within a group are OR (fixed; the supported path for AND
between terms is splitting groups — see Limitations); groups chain with per-group
AND/OR, parentheses generated by the compilers. NOT is intentionally unsupported
(would require coordinated changes across the compilers, the pecan query AST, and all
connectors; 96.md permits omitting NOT when it cannot be added safely).

**Search-run history**: `PecanSearchRun` + `PecanSearchSource` (+`updatedCount`) +
per-page `ScreenImportBatch` rows now carrying `searchRunId`. The Screening
`GET /import-history` endpoint groups batches under their runs (legacy batches via
fileHash parsing) with pagination.

**Provenance**: `ScreenRecordSource` (bare scope keys, no FK; unique per
record+run+batch+provider+providerRecordId; run-scoped idempotency on page retry) is
written at every landing site: file insert, file duplicate-skip, pecan new,
pecan existing-match/exact-dup/fuzzy-dup. `ScreenRecordMetadataChange` logs each filled
field (bounded values). Batch/record deletes and the reset clean both tables.

**Merge policy** (documented in `server/docs/screening-api-contract.md`): match by
DOI → PMID → normalized title; fill-blank-only auto-merge via `mergeFillBlanks`;
`updated` = distinct records per run that gained fields; `already present` = matched,
nothing filled; decisions/stage/status columns are never written by the merge path.

**Reset**: `server/controllers/screeningResetController.js` + `server/screening/resetLock.js`.
Preview endpoint supplies the confirm dialog (counts, scope effects, `confirmToken`,
`blockedBy`). Deletion runs chunked (≤400 ids) inside one transaction (120s cap) with
the job fence re-run as its first statement; landings are blocked by the reset lock at
the shared funnel (`dedupeAndInsertRecords`) and at enqueue (imports, duplicate
detection, pecan `startRun`); in-flight synchronous landings are drained first; the
pecan worker aborts rolled-back runs at page boundaries.

## 4. Database migrations

Additive only (no uniques added to existing tables; all new columns defaulted):
- New tables: `ScreenRecordSource`, `ScreenRecordMetadataChange`, `ScreenResetEvent`.
- `PecanSearchRun` + `origin`, `strategyVersionId`, `questionText`, `rolledBackAt`,
  `rolledBackById`; `PecanSearchSource` + `updatedCount`;
  `ScreenImportBatch` + `searchRunId`, `updatedCount`.

Dev (SQLite): applied via `npx prisma db push` (already run). Postgres: committed
migration `server/prisma/postgres/migrations/20260730000000_search_overhaul_96/`
(generated with `prisma migrate diff` between schema datamodels; the migrations
directory was in sync with the pre-change schema). Deploy sequence:
`npm run db:migrate:deploy:postgres` then `npm run db:generate:postgres` (generated
clients are not checked in). Rollback: the migration is purely additive — restore from
backup per `scripts/verify-restore.mjs` conventions if needed; no destructive step exists.

## 5. Removed legacy components

- PICO in the Search Engine: P/I/C/O cards on the question stage, per-field keyword
  rows, PICO badges/copy, PICO→concept auto-sync, PICO-keyed stage completion and
  quality checks, Strategy Studio PICO headers, engine-registry description.
  (Protocol's PICO module, screening picoSnapshot/AI, manuscript/GRADE uses are
  intentionally untouched — independent features.)
- Concepts stage (merged into Terms & Vocabulary; `?stage=concepts` redirects).
- Search Quality Check: SearchQualityPanel + searchQualityModel deleted; useful checks
  live inline in Terms & Vocabulary re-keyed to generic groups; `?stage=refine` redirects.
- Legacy SearchWizard (3-step) + `searchWorkspaceV2` flag branch + Ops flag toggle;
  ConceptCards; the unreachable standalone step-grid inside SearchBuilderTab (~570
  lines) and its orphans (TermChip, TermEditor, SuggestBox, MeSHDetail, …).
- Compatibility retained: stage aliases in `searchStages.js`; deprecated
  `searchWorkspaceV2` key tolerated in stored settings; legacy blob `SearchTab`
  untouched for `searchEngine`-off deployments.

## 7. Known limitations

1. **Within-group Boolean is fixed to OR.** AND between terms is achieved by splitting
   groups (a visible affordance links to Split). Making the within-group operator
   configurable requires coordinated changes across 16 compilers, the pecan query AST,
   and all 7 connectors; deferred deliberately (same safety rationale 96.md applies to NOT).
2. **NOT is not offered** (see above; 96.md explicitly permits this).
3. The reset lock and landing serialization are **in-process** (the server is
   single-process today). A multi-process deployment must move them to DB advisory
   locks — call sites are funneled and the modules document the migration path.
4. `updated` can in rare cases double-count one record filled simultaneously by two
   concurrent sources of the same run (bounded by source concurrency 3; documented).
5. Pre-96 imports have no provenance rows (the tables are new); their articles show
   provenance only for post-upgrade imports. Legacy shared-provenance (a record found
   by both search and file import before the upgrade) cannot be detected by the reset
   scope and is treated as search-imported.
6. Embase/Cochrane/Scopus/WoS/CINAHL/PsycINFO remain preview/manual-run databases
   (no automated connectors); previews say so honestly.
7. Citation-mining imports during a reset are safely blocked but surface a generic
   error rather than a 409 envelope.

## 8. Deployment

1. `git pull` on the VPS.
2. Postgres: `npm run db:migrate:deploy:postgres` → `npm run db:generate:postgres`.
   (SQLite dev: `npx prisma db push`.)
3. Build: `npm run build` (client) — server restarts via `ecosystem.config.cjs` (PM2).
4. Background workers are in-process; no separate worker deploy. Boot recovery
   re-queues stuck jobs as before; rolled-back runs are refused at page boundaries.
5. No cache invalidation needed (screening/PRISMA counts are computed live; NLM/count
   caches are query-keyed, not record-keyed).
6. Flags: `searchEngine` + `pecanSearch` gate the surfaces as before;
   `searchWorkspaceV2` is deprecated/ignored (stored rows tolerated).
7. Monitoring: watch `ScreenResetEvent` rows and `RESET_IN_PROGRESS`/`JOBS_ACTIVE` 409
   rates after release; `PecanSearchRun.rolledBackAt` non-null counts; Sentry for
   `FENCE_CHECK_FAILED` (fail-closed fence errors).

## 9. Pre-existing bugs found and fixed by this work

1. **Projects list 500 at scale** (`server/screening/metalabAccess.js`): members of
   many workspaces crashed `GET /api/projects` — one large `id IN (...)` combined
   with a `not: null` negation exceeded SQLite's query-parameter limit and Prisma
   cannot auto-split negated queries. Fixed with sequential ≤200-id chunks.
2. **Workspace host unmounted every embedded stage on realtime refetches**
   (`StitchProjectWorkspace.jsx`): each `project.updated` poke replaced the whole
   stage with a loading shell, destroying open dialogs mid-interaction (the reset
   modal died to its own success poke; caught by the new e2e journey). Full-page
   loading/error states now render only when no project is loaded.
3. **Reset modal unmounted by its own section's refresh branches**
   (`ImportHistory.jsx`): the modal now renders in a stable fragment slot across
   loading/error/empty/normal branches.
